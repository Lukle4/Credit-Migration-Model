# Credit Migration Rate Sensitivity Model

Comparing sensitivity of corporate earnings in relation to the 10-Year US Treasury across credit tiers.

Run everything with:

```bash
pip install -r requirements.txt
python run_pipeline.py
```

This prints a full diagnostic report and writes `model_weights.json` (fitted weights + bounds), `evaluation_report.json` (full thesis diagnostics: R², SE, t-stats, noise budget, MSE, Frobenius error), `sheets/Code.gs` (the Google Sheets engine, *generated* from `model_weights.json` -- see point 14) and `credit_migration_scenario_calculator.xlsx` (the Excel workbook, also generated -- see point 15). If the xlsx is open in Excel, that last step is skipped with a message rather than failing the whole run; close the file and re-run.

The same pipeline is also in `credit_migration_model.ipynb`, a self-contained notebook (no `src/` imports, so it runs as-is in Colab) whose Step 5 and Step 6 cells generate the same `Code.gs` and `.xlsx`.

Tests:

```bash
python tests/run_stress.py        # 21 stress checks (incl. the Sheets engine run under Node), against src/ AND the notebook's own code
python tests/js_parity_check.py   # only the Sheets-engine checks of that suite (needs Node.js; reported SKIPPED, never passed, without it)
```

`run_stress.py` executes the notebook, which rewrites `model_weights.json`, `sheets/Code.gs` and the `.xlsx` with identical content (the seed is fixed) -- close the xlsx in Excel first, or that one regeneration is silently skipped for the same open-file reason as above.

## Structure

```
src/
  config.py               all hardcoded constants and ground-truth parameters (ONE source of truth)
  simulate_macro.py        step 1a: macro simulation
  matrix_builder.py        step 2c: shared X-matrix builder (used by both the DGP and the fit)
  markov_dgp.py             step 1b: Markov ground truth (Ptrue) + observed data (Phat_t)
  feature_engineering.py   step 2a/2b: train/test split, log-odds transform, WLS weights
  ols_model.py              step 3: closed-form OLS/WLS engine + Monte Carlo WLS-vs-OLS comparison
  markov_engine.py          step 4: forecasting, cumulative chaining, evaluation, scenario capping (predict_scenario), JSON export
  sheets_export.py          step 5: generates sheets/Code.gs from model_weights.json (JS template + weight injection + verification)
  excel_export.py           step 6: generates credit_migration_scenario_calculator.xlsx from model_weights.json (openpyxl template + weight injection + verification)
tests/
  stress_suite.py           20 stress checks (boundary, negative, fuzzing, config extremes, capping, input validation, both generators, determinism, Sheets engine under Node, Excel structural + golden-value checks); the Node harness is embedded in the file
  run_stress.py             runs the suite against src/ and against the executed notebook
  js_parity_check.py        runs only the Sheets-engine checks of that suite
run_pipeline.py            orchestrates steps 1-6 end to end
credit_migration_model.ipynb   the same pipeline as one self-contained, Colab-ready notebook
sheets/
  Code.gs                   GENERATED, do not edit by hand (see point 14)
  SETUP_GUIDE.md            how to paste it into Google Sheets
credit_migration_scenario_calculator.xlsx   GENERATED, do not edit by hand (see point 15)
```

## Design decisions worth knowing before proofreading

These are the points where the original plan needed a concrete modeling choice that wasn't fully specified, or where a literal reading would have broken something. Each is flagged in code comments at its point of use too.

1. **Tranches**: IG, Non-IG, Junk, Default. Default is an absorbing state (`config.DEFAULT_IDX`) — its row is always `[0,0,0,1]`, never estimated.

2. **Severity model (falling 1, 2, or 3 grades)**: implemented as a cascading continuation-ratio logit per tranche (`markov_dgp.cascade_row`) — Stage A: fall-at-all vs. stay; Stage B: fall≥2 vs. fall=1 (given a fall happened); Stage C: fall=3 vs. fall=2 (given fall≥2). This was chosen specifically because it's the only severity model where every stage reduces to your exact `Y = ln(Pij/Pii)` formula and can be fit with the closed-form `beta_hat = (X'WX)^-1 X'WY` — no substitution of a different estimator (MLE/IRLS) was needed. IG gets 3 stages (can fall up to 3 notches), Non-IG gets 2, Junk gets 1 — bounded by how many tranches exist below each one.

3. **Upgrades**: fixed, non-macro-sensitive constants (`config.UPGRADE_PROB`), one tranche up only. A flagged simplifying assumption — the thesis is scoped to downgrade sensitivity to rates/earnings, and modeling upgrades as macro-sensitive too would double the parameter count with only 48 training quarters to estimate from.

4. **X3 = X1 \* X2 (interaction), not X1 - X2**: the original spec's `X1 - X2` is an exact linear combination of existing columns, making `X'X` singular — the closed-form inverse would fail outright, not just be unstable. The interaction term is a nonlinear combination, keeps the design matrix full rank, and was confirmed with you as the fix.

5. **Feature units**: `X1`/`X2` (delta earnings / delta yield) are expressed in **percentage points** (1.0 = 100bp), not raw decimals. This mattered more than expected — feeding raw decimals in made the true macro signal ~100x smaller than the finite-sample noise, so beta_hat couldn't recover beta_true at all (cosine similarity was often negative). Documented in `matrix_builder.py`.

6. **Macro simulation is mean-reverting to a deterministic *cyclical* target, not a flat constant**: a mean-reverting process pinned to a fixed constant has no source of variation except its own shocks — "minimizing noise" in that setup would shrink the entire signal to nothing along with it, not just the noise. The 10Y yield instead mean-reverts to a slow sine-wave cycle (`config.YIELD_CYCLE_*`, an 8-year hike/cut cycle) with small shocks around it, so there's genuine macro-driven variation for beta to explain while shocks stay a minority of the total variance. `simulate_macro.noise_budget_report()` prints the realized noise-to-signal ratio and flags any quarter with a |z|>3 outlier move on every run, per your request — currently ~0.54 for yield, ~0.36 for earnings, 0 outlier quarters.

7. **Numerical conditioning**: the raw design matrix (intercept ~O(1) vs. macro deltas ~O(1)) is fine after the percentage-point fix (condition number ~100), but `ols_model.fit_ols` still applies exact column-norm preconditioning (fit on `X/s`, divide the result back by `s`) as a general numerical-stability safeguard, and cross-checks every fit against `np.linalg.lstsq` (SVD-based) to catch any disagreement. beta_hat is returned in the same raw units as beta_true, so the beta_hat-vs-beta_true comparison is direct, not scale-adjusted.

8. **Company pool / sampling noise**: `Phat_t` (the "observed" dataset) is simulated as a multinomial draw of `config.COMPANY_POOL_SIZE` = 3000 companies per source tranche per quarter from `Ptrue`'s row probabilities — this is where genuine finite-sample noise enters the pipeline (separate from the macro shock noise in point 6). Zero/near-zero counts are handled with additive (Laplace) smoothing (`config.SMOOTHING_EPSILON`) only at the point of computing log-odds in `feature_engineering.py` — the raw stored counts are never smoothed, so they stay genuinely "observed." **Deliberately uniform across tranches, not a claim about real-world universe sizes**: real corporate bond markets don't have equal numbers of IG, Non-IG, and Junk-rated issuers (most real universes skew investment-grade). Using the same 3000 for all three tranches is a stated simplifying assumption, kept intentionally rather than calibrated to any actual rating-agency universe statistics — flag this explicitly if the thesis compares this model's implied precision across tranches to what a real universe's differing sample sizes would give you.

9. **Weighted least squares, not plain OLS**: `Y_t = ln(n_fall/n_stay)` is a log-ratio of finite counts, whose variance (delta method: `~= 1/n_fall + 1/n_stay`) differs every quarter — a quarter with 40 observed events is far more informative than one with 2. Plain OLS treats every quarter as equally reliable, understating uncertainty and wasting signal, especially for the rare Stage B/C events. `ols_model.fit_ols` now accepts an optional `weights` argument and defaults every real fit to WLS, with weights computed from the same smoothed counts used for `Y` (`feature_engineering.build_Y_and_W_by_stage`) and winsorized (`config.WLS_WEIGHT_CAP_MULTIPLE`) so a single unstable low-count quarter can't dominate. On the current data that cap never actually binds (no quarter's weight exceeds 5x its stage median), so it is a safeguard, not something shaping the results. **Caveat found during testing, worth knowing**: a single-seed comparison can be actively misleading for the sparsest stages — on the original seed, IG-B's cosine similarity to `beta_true` looked much worse under WLS (0.525) than plain OLS (0.960). Repeating the company-pool draw 40 times with the same macro path (`ols_model.monte_carlo_wls_vs_ols`, run automatically by `run_pipeline.py`) shows this was mostly noise: averaged out, WLS has the higher mean cosine similarity in 5 of 6 stages, but **every** difference is within one standard deviation, so the honest reading is a toss-up: there is no evidence that WLS is better or worse than OLS on this data (IG-B, the one stage where WLS is lower, is 0.734 for OLS vs 0.710 for WLS). Don't claim WLS "wins" in the thesis; the case for WLS is the delta-method variance argument above, not a measured accuracy gain. Root cause: 12 of IG-B's 48 training quarters have literally zero observed "fell 2+ notches" events, which is a data-scarcity problem no reweighting scheme can fully fix, not a WLS bug — `fit_ols`'s own WLS-with-uniform-weights-equals-plain-OLS check (`validate_wls_reduces_to_ols`) confirms the weighting math itself is correct.

   **R² comparability note**: since `fit_ols` now computes weighted SSE/SST under WLS, its reported R² is on the *weighted* scale, not the classical unweighted one. If you're citing R² values in the thesis, say so explicitly — a weighted R² isn't directly comparable to a plain-OLS R² from elsewhere (or to R² values from any earlier draft of this pipeline, before WLS was added), even though both are called "R²".

10. **Extrapolation guard and capping**: `beta_hat` is linear-in-the-logit and was only ever fit on macro deltas roughly in the ±1 percentage-point range (`markov_engine.compute_x_train_bounds`). Nothing in the math stops it being queried on a wildly larger scenario, and there it doesn't just get unreliable, it *saturates*: the sigmoid returns a literal 0%/100% (e.g. "100% of IG demotes in one quarter"), which has no historical precedent however "correct" it is for a linear model extrapolated that far. Two mechanisms, both in `markov_engine.predict_scenario` (the "what if" entry point that Sheets/Excel mirror; batch evaluation on real test data goes through the separate, uncapped `forecast_transition_tensor`):

    - `assess_scenario_range` flags any input outside the training range. It is evaluated against the RAW input and never blocks, since a deliberate stress test may be exactly what's being explored.
    - `cap_scenario_to_bounds` clamps the input before the sigmoid runs, with per-feature bounds (`config.EXTRAPOLATION_CAP_*`): earnings 3x its own training range (about [-2.34, +1.94]), yield an explicit [-2.0, +10.0], interaction 15x its own range (about [-3.60, +0.67]). X3 is recomputed from the capped X1·X2 and then clamped, because capping X1 and X2 alone doesn't bound their product. It is not one shared multiplier because earnings and yield saturate at very different multiples of their own training range. The resolved bounds are exported as `extrapolation_cap_bounds` in `model_weights.json`, so Sheets/Excel only ever clip against three plain `[lo, hi]` pairs.

    **State these in the thesis**: beyond the caps the output is static (a plateau, not a continuing trend), and the caps are a judgement call about where the fitted model is still informative, not something estimated from data. Known residual: the worst combined corner (earnings -2.34, yield +10) still leaves IG-stay at only about 0.04%.

11. **Numerically stable sigmoid**: `markov_dgp._sigmoid` branches on the sign of `z` so the argument passed to `exp()` is always ≤0, eliminating `exp()` overflow for very negative `z` — a real risk once out-of-range scenarios (point 10) are deliberately allowed through rather than blocked. Ported identically into `sheets/Code.gs`.

12. **Input validation (Python and Sheets)**: `predict_scenario` and the Sheets functions reject NaN, infinite and non-numeric scenario inputs with a clear error; `PREDICT_ROW` rejects an unrecognized tranche name; `CUMULATIVE_STEADY` requires a whole-number horizon from 1 to 1000. These were found by probing, not by reading: before the fix a NaN scenario returned an all-NaN matrix (Python: with no range warning, because NaN comparisons are always False, and `was_capped=True`; Sheets: with `SCENARIO_WARNING` saying "OK - within training range"), `±inf` was silently clamped into a plausible-looking answer, a blank cell threw the cryptic `toFixed is not a function`, `2.7` quarters was silently floored to 2, and a horizon of `Infinity` or `1e9` hung the sheet until Apps Script's timeout.

13. **Stress suite (21 checks)**: boundary values, malformed input that must fail loudly, 300-trial property-based fuzzing, config extremes (e.g. `SMOOTHING_EPSILON = 0` must reintroduce `ln(0)`, proving the epsilon is load-bearing), capping, non-finite input, both generators (point 14, 15), the generated `Code.gs` executed under Node, the generated Excel workbook's internal structure and a real-Excel golden value, determinism, and cross-seed invariance of the pipeline's own sanity checks. A check can also report SKIP (for example when Node isn't installed, or when `model_weights.json`/the workbook aren't on disk yet): that is printed as not tested and is never counted as a pass. The same suite is the notebook's own stress-test cell, so it runs inside Colab too. `tests/run_stress.py` runs it against `src/` and against the notebook's own code executed fresh, so a notebook that drifts from `src/` shows up as a divergence instead of being trusted because it was built from `src/`.

14. **The Sheets engine is generated, not hand-maintained**: Apps Script can't run inside Jupyter, so `src/sheets_export.py` holds the JavaScript engine as a fixed template, injects the whitelisted keys of `model_weights.json` into it, and reads them back out of the generated text to verify they are identical. It refuses weights the JS can't handle (NaN, a missing stage, a renamed tranche, inverted cap bounds, or an IG upgrade probability above 0, which the JS would write to row index -1). `run_pipeline.py` and notebook Step 5 both call it, so a re-fit can no longer leave a Sheet running stale, hand-pasted weights. Never edit `sheets/Code.gs` directly; edit the template. The stress suite runs the generated file under Node: it matches the Python engine to about 2e-16 over 204 scenarios (in-range to ±1000), and the file on disk must be byte-identical to the generator's output, so a stale or hand-edited copy fails. **Not covered**: Apps Script itself has never been executed. Node stubs `SpreadsheetApp`, so the custom functions' math is verified but `setupSheet()` (layout, formatting, heatmap rules) is not.

15. **The Excel workbook is also generated, and was rebuilt to fix two confirmed bugs**: `src/excel_export.py` builds `credit_migration_scenario_calculator.xlsx` (README / Scenario / Model_Weights / a hidden Calc sheet) from `model_weights.json` with openpyxl, using the same weight-injection-then-verify discipline as point 14 (same bad-weight rejections, checked by `tests/stress_suite.py`'s Excel checks). `run_pipeline.py` and notebook Step 6 both call it; if the file is open in Excel the step is skipped with a message rather than crashing the run. Never edit the workbook's Calc or Model_Weights tabs by hand.

    The previous, hand-built version of this workbook had two confirmed bugs, found by inspecting its raw XML (not guessed): its heatmap used Excel's `x14` extended conditional-formatting format -- which openpyxl's own reader warns it can't parse back -- anchored to a **fixed, absolute** `Calc!B288` cell that was past the last real cumulative-matrix block (quarter 60 ends at row 284) and never corresponded to any horizon; and the displayed matrix cells held `=TEXT(...,"0.00%")` formulas, i.e. text, not numbers, and Excel's conditional formatting does not evaluate colour scales on text cells -- independently enough to explain "colours missing" on its own. Both are fixed in the rebuild: the displayed cells are plain numeric formulas with `number_format` set directly, and both heatmaps are standard (non-extended) `ColorScaleRule`s applied straight to the displayed ranges, so they always track whatever is on screen instead of a hand-computed absolute row.

    **What is and isn't verified**: unlike the Sheets engine, nothing in this environment can execute Excel formulas (no Excel, no LibreOffice), so the regenerated formulas are never run end to end by a real spreadsheet engine. `verify_workbook` (called automatically by the generator) checks the embedded weights against `model_weights.json` exactly, and separately recovers the cumulative chain's intended length from the horizon cell's own data-validation bound and confirms every MMULT block, and the Scenario sheet's own INDEX formula, reference rows inside that bound -- the precise class of the historical `B288` bug, mutation-tested by deliberately reintroducing that exact bug shape and confirming it's caught. As a check that the underlying cascade/MMULT formula *math* (as opposed to the display/CF layer that was rebuilt) was always correct, the stress suite also replays a scenario's values that were cached in the *old* workbook by a real copy of Excel (captured before the rebuild) and confirms the Python engine still reproduces them exactly (`check_excel_workbook_matches_real_excel_calculation`) -- but this is a frozen fixture checked against Python, not a live check of the current file's formulas.

    **A third, real bug, found only by opening the file in Excel**: the generator's tranche-row column placement was hardcoded ("the upgrade always lands in column B, the tranche's own data always starts at column C"), which is only correct for NonIG (upgrade target position happens to equal the hardcoded column) and silently wrong for Junk -- its 5% upgrade landed in the `->IG` column instead of `->NonIG`, its stay probability landed in `->NonIG` instead of `->Junk`, and `->Default` was never written at all (left blank, read as 0 downstream). Neither of the two checks above could have caught this: the cell was populated and in-bounds, just holding the wrong quantity. Fixed by deriving the column from the tranche's actual position (`2 + idx` for its own diagonal, `2 + idx - 1` for any upgrade) instead of a value that only worked by coincidence for one case, and by adding `check_excel_workbook_cascade_matches_python`: a small symbolic evaluator (inlined into `stress_suite.py`, not a separate importable module, so it travels into the notebook copy the same way the Node harness does) that recomputes what the Calc sheet's cascade-logit formulas actually encode -- across in-range scenarios and several deliberate outliers beyond the training range -- and cross-checks every tranche's row against `cascade_row`, the trusted Python engine. That check also re-mutates a fresh build into the exact original bug shape on every run and confirms it's still detected, rather than trusting a one-off manual confirmation.

    **Also de-hardcoded** (found during the same fix, not separately reported bugs -- they hadn't yet had a chance to break, but were the same brittle pattern): the tranche list used to loop over cascade blocks was a module-level `["IG","NonIG","Junk"]` constant instead of being read from `model_weights["tranches"]`; the Scenario sheet's matrix-block rows were literal numbers instead of a running cursor; and `verify_workbook`'s conditional-formatting-range check compared against a separately hand-typed `{"B11:E14","B19:E22"}` instead of discovering the actual ranges the same way the sheet itself was built (by locating each block's title label). All four are now derived from a single source of truth. The shared validator also now rejects a `max_fall` deep enough to fall past Default -- the same implicit assumption both the JS (`row[idx+k]`) and Excel (`column 2+idx+k`) engines make, previously unchecked.

## Data leakage checks

- **Chronological split only**: `feature_engineering.train_test_indices()` splits quarters 1–48 (train) / 49–60 (test) in time order. A random shuffle would leak future autocorrelated macro information into training and was explicitly avoided.
- **Ptrue is never used for fitting anything** — only for the final step-4 evaluation (comparing the forecasted cumulative test-period matrix against the true one). Everything in steps 2–3 is built exclusively from `Phat_t`.
- **No feature standardization was needed** (see point 7 above), so there are no train-set-only scaling constants that could otherwise leak if mishandled between Python and the Apps Script side.
- **Multi-period cumulative probability uses sequential matrix multiplication** (`P(t1) @ P(t2) @ ... @ P(tn)`), not a matrix power — the quarterly matrices are macro-varying (non-homogeneous), so `P^n` would silently assume a constant chain and misstate the true multi-period probability.

## Known limitations (flagged, not bugs)

**Deeper cascade stages are noisy.** Stage B, and especially Stage C for IG ("given a fall already happened, does it go all the way to default"), fit much worse than Stage A (R² 0.03 to 0.31 vs. 0.84 to 0.98 for Stage A). This is expected: they are rare conditional events with far fewer observations in only 48 training quarters (12 of IG-B's 48 quarters have zero "fell 2+" events), so it deserves a paragraph in the thesis discussion rather than a "fix". `engine_sanity_check` in `ols_model.py` confirms the OLS/WLS engine and cascade math are exactly correct on noiseless data (max error ~1e-14), which isolates this from being an implementation bug. WLS (point 9) cannot manufacture more data. `monte_carlo_wls_vs_ols`'s output (printed by `run_pipeline.py`, saved in `evaluation_report.json` under `wls_vs_ols_monte_carlo`) is the seed-independent picture of where the model is and isn't reliable; cite it rather than a single run's R² or cosine similarity. The stored R² values are on the weighted scale (point 9) and are not comparable to a plain-OLS R².

**Cosine similarity flatters Stage A.** Stage A's ~0.995 to 0.999 is dominated by the large intercept. The coefficients the thesis is actually about (the macro sensitivities, especially the interaction term) are recovered much less tightly: IG-A's interaction coefficient is about -0.88 against a true -0.4, with t ≈ -1.35, i.e. not significant. Report coefficient-level errors and standard errors, not just cosine similarity.

**`BETA_TRUE` is an assumption, not a finding.** The values in `config.py` are hardcoded. The structure (tranches differ in macro-sensitivity, with lower tranches more sensitive) is the thesis premise; the magnitudes are synthetic and not derived from theory or real rating-transition data. Recovering them shows the estimator works. It is not evidence about real credit markets. Likewise the uniform company pool (point 8) is a simplifying assumption.
